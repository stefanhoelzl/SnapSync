## Why

The relational store's migration mechanism is entirely hand-rolled — an ordered list of TypeScript
`Migration` objects, a bespoke runner, a bespoke version table, and a bespoke exit-code protocol that
decides whether a deploy opens a maintenance window. bunny now ships `bunny db migrations`, which does
the same job over plain `.sql` files against the same store, authenticating with the two database
credentials CI already holds — so no bunny **account** key is required and `backend-deployment`'s
least-privilege rule is untouched.

Three things make the swap worth taking now rather than later:

1. **The hand-rolled runner tracks version NUMBERS only.** Edit a shipped migration's statements and it
   applies nothing and reports success — the exact silent-success failure `migrations.ts`'s own header
   was written about. The CLI checksums every file and refuses to apply over a modified history.
2. **The hand-rolled runner applies migrations with foreign keys ENABLED**, because a bare
   `db.batch(…, "write")` inherits bunny's `PRAGMA foreign_keys` default of 1. Measured: under that
   regime a rebuild of a parent table silently empties its children, because SQLite treats
   `DROP TABLE` as an implicit `DELETE` that fires `ON DELETE CASCADE`. The obvious fix is a silent
   no-op — `PRAGMA foreign_keys` is ignored inside a transaction, and the batch *is* the transaction.
   The CLI brackets each file with `PRAGMA foreign_keys=off` outside the transaction and inside one
   wire request, which is the only construction that satisfies both constraints.
3. **`SCHEMA` is a hand-maintained duplicate whose stated purpose is false.** `database` justifies it as
   "how every fresh dev and test store comes into being", but nothing creates from it — the rig and
   every test replay migrations, and its only consumer is one test.

The exploration behind this change also found a latent defect independent of the switch: migration v3
copies with `INSERT … SELECT *`, which silently transposes values if a rebuild ever reorders columns.
Measured: every existing guard passes while `attest_key` and `attest_env` swap places.

## What Changes

- Migrations become numbered `.sql` files under `api/migrations/`, applied in CI by
  `bunny db migrations apply`, tracked in `__bunny_migrations` with checksums.
- **BREAKING (internal)**: `src/migrations.ts`'s `MIGRATIONS` list, its runner and
  `src/scripts/migrate.ts` are removed. v1–v4 are squashed into `0001_baseline.sql`, which is the
  current schema plus `DROP TABLE IF EXISTS schema_migrations`. Applying it to the deployed store is
  inert — measured: the live store's shape already equals a replay of v1–v4.
- A small in-repo replayer applies the same `.sql` files for the local rig, the test fixtures and the
  schema generator, since the CLI refuses any non-encrypted URL and so cannot target a local store. It
  brackets each file with `PRAGMA foreign_keys=off/on`, matching the CLI exactly.
- **`SCHEMA` in `db.ts` is removed.** The schema is instead GENERATED by replaying migrations and
  dumping `sqlite_master`, committed, with CI failing when it is stale — the pattern `architecture/`
  already uses.
- Preconditions move from TypeScript callbacks to an in-file SQL `RAISE(ABORT)` guard, so the refusal
  travels with the migration and shares its transaction. Refusal messages become static and name the
  diagnostic query instead of interpolating a count.
- New authoring rule: a migration's `INSERT … SELECT` SHALL NOT use `SELECT *`.
- New deploy assertion: the live store's shape is compared against the committed snapshot — as a
  pre-flight when no migration is pending, and after applying when one is.
- The maintenance-window decision moves from `migrate.ts --pending` to a thin wrapper over
  `bunny db migrations list --output json`, preserving the same 0 / 10 / other contract.

## Capabilities

### New Capabilities

None. Every change lands inside two existing capabilities.

### Modified Capabilities

- `database`: the migration mechanism (ordered `.sql` files, checksummed, applied by the CLI);
  the two-forms requirement (the created form becomes GENERATED, and its false rationale is corrected);
  the precondition mechanism (declared callback → in-file SQL guard, with a static message); a new
  requirement banning `SELECT *` in a migration's row copy; and a statement that migrations apply with
  foreign-key enforcement off.
- `backend-deployment`: the migrate step's command and the producer of the pending contract; a new
  requirement that a deploy asserts the live store's shape against the committed snapshot, in the two
  positions the pending answer already splits on.

## Impact

- **Code**: `api/src/migrations.ts` and `api/src/scripts/migrate.ts` removed; `SCHEMA` removed from
  `api/src/db.ts`; new `api/migrations/*.sql`, a replayer, a schema generator, and a pending-check
  wrapper; `api/test/migrations.test.ts` rewritten against files rather than the TS list.
- **Callers**: `api/src/dev/serve.ts` and `api/test/support/harness.ts` move from `migrate()` to the
  replayer.
- **CI**: `api-deploy.yml` installs `@bunny.net/cli` (unpinned, by decision), replaces the two migrate
  steps, and gains the shape assertion. `api.yml` gains the snapshot-freshness check.
- **Deployed store**: the cutover deploy WILL open a maintenance window — `__bunny_migrations` starts
  empty, so the baseline reports as pending even though applying it changes nothing. The bundle-archive
  rollback path must be healthy going in.
- **Dependencies**: a new CI toolchain (`@bunny.net/cli`, ~208 MB, self-labelled *experimental* for
  `db migrations`). No new credentials: `--url`/`--token` are the secrets CI already holds.
- **Not affected**: the device's SQLDelight migrations, the storage zone, and the sweep.
